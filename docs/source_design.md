# Source System Design

This document describes the two synthetic source systems behind the Northline Outfitters people analytics pipeline, the data problems deliberately planted in them, and the business questions the pipeline exists to answer.

Northline Outfitters is a fictional company. Both source systems are simulations, generated by Python scripts in this repository. The data problems are planted on purpose: each one is a realistic issue found in real HR data, and each one forces the pipeline to demonstrate a specific technique for handling it.

## 1. The scenario

Northline Outfitters is a fictional Canadian outdoor retail company with about 250 employees across a head office, a distribution centre, and a dozen stores. The company has grown through hiring bursts and one small acquisition. Its people data lives in two systems that were never designed to talk to each other:

- **PeopleCore (HRIS)** is the HR system of record: who works here, their role, department, and employment dates. It exports a nightly CSV of all employees. The company adopted it in 2019, so anyone hired before then was migrated in with backfilled records.
- **TalentFlow (ATS)** is the recruiting system: candidates, applications, and offers. It exports JSON. The company adopted it in 2022, so it has no history of anyone hired before then.

Nobody has ever reconciled these systems. HR answers headcount questions from PeopleCore exports in spreadsheets, and recruiting reports come from TalentFlow's built in charts. The numbers disagree and nobody is sure why. This pipeline is the first attempt to build one trusted view.

## 2. PeopleCore (HRIS) export: employees.csv

One row per employment record, not per person. The distinction matters: if someone leaves and is later rehired, they appear as two rows with two different employee IDs and nothing connecting them. The export is a nightly full dump, meaning every run contains all current records rather than just the changes since yesterday.

| Field | Type | Notes |
|---|---|---|
| employee_id | string | Format `E-04211`. Assigned at hire, never reused. A rehired person gets a new ID. |
| first_name | string | As entered by HR, so it can differ from other systems ("Rob" here, "Robert" elsewhere) |
| last_name | string | Can change over time (marriage, correction) |
| work_email | string | Pattern first.last@northline.ca, which collides when two employees share a name |
| personal_email | string | Sometimes blank, sometimes outdated |
| department | string | Free text with drift: "Retail Ops", "Retail Operations", and "retail ops" all appear |
| job_title | string | Changes with promotions. Only the current value is visible in any export. |
| employment_type | string | FT, PT, Contract, with inconsistent casing |
| hourly_or_salary | string | Only populated for records created after 2021, blank before |
| salary_band | string | B1 through B6, with some blanks |
| hire_date | date | For employees migrated in 2019, some dates are the migration date rather than the true hire date |
| termination_date | date | Blank if active. Occasionally entered late, days after the person actually left. |
| status | string | Active, Terminated, On Leave |
| last_modified | timestamp | When HR last touched the record |

Design notes:

- A full export has no memory. If a job title changes, yesterday's value is gone unless the pipeline was already saving history. Constructing that history is one of the pipeline's jobs.
- The department field needs cleanup and mapping before it can be trusted for reporting.
- The migrated hire dates cannot be fixed, only flagged. Tenure calculations need to handle them honestly.
- The last_modified timestamp helps decide which record to trust when systems disagree.

## 3. TalentFlow (ATS) export: candidates.json

One JSON object per candidate, with that person's applications nested inside. A candidate who applies three times over the years is one record with three applications. Like PeopleCore, this is a full dump.

Example structure:

```json
{
  "candidate_id": "cand_8f3k2",
  "first_name": "Robert",
  "last_name": "Chen",
  "personal_email": "rchen.mail@gmail.com",
  "phone": "416-555-0142",
  "created_at": "2023-04-11T14:22:09Z",
  "applications": [
    {
      "application_id": "app_x92m1",
      "job_title": "Retail Associate",
      "department": "Retail Operations",
      "applied_at": "2023-04-11",
      "status": "hired",
      "offer": {
        "accepted_at": "2023-05-02",
        "start_date": "2023-05-15"
      }
    }
  ]
}
```

Field notes:

| Field | Notes |
|---|---|
| candidate_id | Format `cand_8f3k2`. TalentFlow's best guess at one record per person. Its deduplication is imperfect. |
| first_name / last_name | Self reported by the candidate, so they can differ from HR's records |
| personal_email | The primary signal for matching candidates to employees, but people change emails between applications |
| phone | A secondary matching signal, stored in inconsistent formats: dashes, no dashes, some with a +1 country code |
| applications[].status | rejected, withdrawn, in_progress, hired |
| applications[].offer | Only present when status is hired. Contains accepted_at and start_date. |

Design notes:

- There is no employee_id and no work_email here. A recruiting system meets people before they become employees, so those fields cannot exist. Matching TalentFlow records to PeopleCore records has to rely on human attributes like names and personal emails, which are unreliable. That asymmetry is the central challenge of this project.
- The nested structure means the pipeline has to unnest applications into rows before modeling, a different task than reading a flat CSV.
- A hired application with an accepted offer creates a testable expectation: that person should appear in PeopleCore shortly after their start date. Some planted problems are violations of exactly that expectation.

## 4. The planted problems

Each problem below follows the same pattern: what it is, why it happens in real companies, and what it forces the pipeline to do. Together they double as the test cases for the transformation layer.

### Structural problems

**P1. Format mismatch.** One source is a flat CSV, the other is nested JSON.
Why it happens: every vendor exports differently, and no company gets to pick one format for all its systems.
What it forces: a staging layer that conforms both sources into clean, consistently typed and named tables, including unnesting the JSON applications array.

**P2. Grain mismatch.** PeopleCore is one row per employment record. TalentFlow is one record per candidate, with applications nested inside. No table in either source is one row per person.
Why it happens: each system models what it cares about, not what analytics needs.
What it forces: an explicit statement of grain for every model, and a deliberately constructed person level table that no source system provides.

**P3. Exports with no memory.** Both systems export current state only. Past values of any field are gone unless the pipeline saved them.
Why it happens: nightly full dumps are the most common export pattern in HR software.
What it forces: snapshots that capture changes over time, feeding a slowly changing dimension that can answer point in time questions like "what was headcount by department in March."

### Identity problems

**P4. The rehire.** One person, two employment records, two employee IDs, and nothing connecting them. The data includes at least two rehires: one clean case (same personal email both times) and one hard case (email changed between stints).
Why it happens: HR systems track employment records, not people, and retail turnover makes rehires routine.
What it forces: identity resolution that builds a canonical person identifier which survives rehires.

**P5. Duplicate candidates.** One person exists as two candidate records in TalentFlow because they applied years apart with different email addresses.
Why it happens: candidates self report their contact information, and contact information changes.
What it forces: deduplication within a single source before any cross source matching starts.

**P6. Name drift across systems.** "Robert Chen" in TalentFlow is "Rob Chen" in PeopleCore. One person's last name changed after marriage in one system but not the other.
Why it happens: different people type into different systems at different times.
What it forces: matching logic that cannot rely on exact name equality. The approach: match on personal email first, fall back to name plus a corroborating signal, and flag ambiguous cases for review instead of silently guessing.

**P7. Work email collision.** Two different employees with the same name, producing colliding or suffixed work emails (sarah.lee@ and sarah.lee2@).
Why it happens: name based email patterns guarantee collisions at any real company.
What it forces: proof that email is not a person identifier, and a uniqueness test on the canonical person key.

### Data quality problems

**P8. Department name drift.** "Retail Ops", "Retail Operations", and "retail ops" all appear.
What it forces: a standardization mapping table, with a test that fails loudly when a new unmapped value shows up.

**P9. Inconsistent formats in matching fields.** Phone numbers with and without dashes and country codes, emails with mixed casing.
What it forces: standardization in staging before any matching logic runs, since dirty match keys produce silent match failures.

**P10. Migrated hire dates.** Some employees hired before 2019 carry the 2019 migration date as their hire date.
What it forces: a flag column identifying affected records, and tenure metrics that exclude or caveat them. This problem cannot be fixed, only surfaced honestly.

**P11. Late termination dates.** Some termination dates were entered days after the person actually left, so the historical record briefly shows someone as active who was not.
What it forces: awareness that even corrected data and historical snapshots can disagree, documented in the metric definitions.

**P12. The no show.** One candidate has a hired status and an accepted offer but never appears in PeopleCore.
Why it happens: people accept offers and never start, and someone forgets to update the recruiting system.
What it forces: a reconciliation test between the two systems, and an explicit rule for which system wins. Here, the HRIS is the system of record for employment.

**P13. Start date disagreement.** One hired candidate's start date in TalentFlow differs from their hire date in PeopleCore by a few days.
Why it happens: start dates move after offers are signed.
What it forces: a tolerance rule (dates within a few days are treated as the same event) and a decision about which date is authoritative.

## 5. Business questions

The models exist to answer these questions. Working backward from questions is the design principle: if a model does not help answer one of them, it does not need to exist.

### Headcount

- How many people work at Northline today, overall and by department?
- How has headcount changed month over month? Answering this for any past date requires the historical dimension built from snapshots, because the raw exports only know the present.
- What is the split between full time, part time, and contract?

One definition to document and test: who counts in headcount. This project counts employees with status Active or On Leave as of a stated date, with contractors shown separately. Every chart uses this single tested definition.

### Turnover and retention

- What is monthly and annual turnover, overall and by department?
- Are certain departments losing people faster? This requires knowing each person's department at the time they left, not their most recent one.
- What is average tenure, with the migrated date records (P10) flagged or excluded?

### Rehires

- How many current employees are rehires? What share of each year's hires are returning employees?
- Neither source system can answer this on its own, because neither one knows that two employment records belong to the same person. Only the canonical person record built by this pipeline can answer it.

### Recruiting to employment

- How long does it take from application to start date?
- What share of accepted offers convert into actual employment? This is the check that catches the no show (P12).
- Which departments hire mostly through TalentFlow? Employees hired before 2022 legitimately have no recruiting record, so absence has to be interpreted carefully.

The dashboard focuses on headcount and turnover, with rehire and recruiting insights as supporting views.
