# Source System Design

This document describes the two synthetic source systems behind the Northline Outfitters people analytics pipeline, the data problems planted in them, and the questions the pipeline exists to answer.

Northline Outfitters is a fictional company and both source systems are simulations, generated by Python scripts in this repository. The data problems are planted on purpose. Each one is a realistic issue found in real HR data, and each one forces the pipeline to demonstrate a specific technique for handling it.

## 1. The scenario

Northline Outfitters is a fictional Canadian outdoor retailer with about 190 employees across a head office, a distribution centre, and a dozen stores. Its people data lives in two systems that were never designed to talk to each other:

- **PeopleCore (HRIS)** is the HR system of record. It knows who works here, their role, department, and employment dates, and exports a nightly CSV of all employees.
- **TalentFlow (ATS)** is the recruiting system. It knows candidates, applications, and offers, and exports JSON. The company adopted it in 2022, so it has no record of anyone hired before then.

Nobody has ever reconciled these systems. HR answers headcount questions from PeopleCore exports in spreadsheets, and recruiting reports come from TalentFlow's built in charts. The numbers disagree and nobody is sure why. This pipeline is the first attempt to build one trusted view.

## 2. PeopleCore (HRIS) export: employees.csv

One row per employment record, not per person. That distinction matters: if someone leaves and is later rehired, they appear as two rows with two different employee IDs and nothing connecting them. The export is a nightly full dump, so every run contains all current records rather than just what changed.

| Field | Type | Notes |
|---|---|---|
| employee_id | string | Format `E-04211`. Assigned at hire, never reused. A rehired person gets a new ID. |
| first_name | string | As entered by HR, so it can differ from other systems ("Rob" here, "Robert" elsewhere) |
| last_name | string | Can change over time, usually after marriage |
| work_email | string | Pattern first.last@northline.ca, which collides when two employees share a name |
| personal_email | string | Sometimes blank |
| department | string | Free text with drift: "Retail Ops", "Retail Operations", and "retail ops" all appear |
| job_title | string | Changes with promotions. Only the current value is visible in any export. |
| employment_type | string | FT, PT, Contract, with inconsistent casing |
| salary_band | string | B1 through B6, with some blanks |
| hire_date | date | The date this employment record began |
| termination_date | date | Blank if the person is still employed |
| status | string | Active, Terminated, On Leave |
| last_modified | timestamp | When HR last touched the record |

Design notes:

- A full export has no memory. If a job title changes, yesterday's value is gone unless the pipeline was already saving history. Building that history is one of the pipeline's jobs.
- The department field needs cleanup and mapping before it can be trusted for reporting.
- The last_modified timestamp helps decide which record to trust when systems disagree.

## 3. TalentFlow (ATS) export: candidates.json

One JSON object per candidate, with that person's applications nested inside. A candidate who applies three times over the years is one record with three applications. Like PeopleCore, this is a full dump.

Example structure:

```json
{
  "candidate_id": "cand_8f3k2",
  "first_name": "Robert",
  "last_name": "Chen",
  "personal_email": "rchen.mail@gmail.com",
  "phone": "416-555-0142",
  "created_at": "2023-04-11T14:22:09Z",
  "applications": [
    {
      "application_id": "app_x92m1",
      "job_title": "Retail Associate",
      "department": "Retail Operations",
      "applied_at": "2023-04-11",
      "status": "hired",
      "offer": {
        "accepted_at": "2023-05-02",
        "start_date": "2023-05-15"
      }
    }
  ]
}
```

Field notes:

| Field | Notes |
|---|---|
| candidate_id | Format `cand_8f3k2`. TalentFlow's best guess at one record per person. Its deduplication is imperfect. |
| first_name / last_name | Self reported by the candidate, so they can differ from HR's records |
| personal_email | The main signal for matching candidates to employees, but people change emails between applications |
| phone | A second matching signal, stored in inconsistent formats: dashes, no dashes, some with a +1 country code |
| applications[].status | rejected, withdrawn, in_progress, hired |
| applications[].offer | Only present when the status is hired. Contains accepted_at and start_date. |

Design notes:

- There is no employee_id and no work email here. A recruiting system meets people before they become employees, so those fields cannot exist. Matching these records to PeopleCore has to rely on names and personal contact details, which are unreliable. That asymmetry is the central challenge of this project.
- The nested structure means the pipeline has to unnest applications into rows before modelling, a different task than reading a flat CSV.
- A hired application with an accepted offer creates a testable expectation: that person should appear in PeopleCore shortly after their start date. One planted problem is a violation of exactly that.

## 4. The planted problems

Each problem below follows the same pattern: what it is, why it happens in real companies, and what it forces the pipeline to do. Together they are the test cases for the transformation layer.

### Structural problems

**P01. Format mismatch.** One source is a flat CSV, the other is nested JSON.
Why it happens: every vendor exports differently, and no company gets to pick one format for all its systems.
What it forces: a staging layer that conforms both sources into clean, consistently typed tables, including unnesting the JSON applications.

**P02. Grain mismatch.** PeopleCore is one row per employment record. TalentFlow is one record per candidate, with applications nested inside. No table in either source is one row per person.
Why it happens: each system models what it cares about, not what analytics needs.
What it forces: a clear statement of what one row means in every model, and a person level table that no source system provides.

**P03. Exports with no memory.** Both systems export current state only. Past values of any field are gone unless the pipeline saved them.
Why it happens: nightly full dumps are the most common export pattern in HR software.
What it forces: snapshots that capture changes over time, feeding a slowly changing dimension that can answer questions like "what was headcount by department in March."

### Identity problems

**P04. The rehire.** One person, two employment records, two employee IDs, and nothing connecting them. The data includes two rehires: one easy case with the same personal email both times, and one hard case where the email changed between stints.
Why it happens: HR systems track employment records, not people, and retail turnover makes rehires routine.
What it forces: identity resolution that builds a person identifier surviving rehires.

**P05. Duplicate candidates.** One person exists as two candidate records in TalentFlow because they applied years apart with different email addresses.
Why it happens: candidates self report their contact information, and contact information changes.
What it forces: deduplication within a single source, before any cross source matching starts.

**P06. Name drift across systems.** "Robert Chen" in one system is "Rob Chen" in the other. One person's last name changed after marriage in one system but not the other.
Why it happens: different people type into different systems at different times.
What it forces: matching that cannot rely on names being identical. The approach is to match on personal email first, fall back to name plus a second corroborating signal, and flag ambiguous cases instead of guessing.

**P07. Work email collision.** Two different employees share a name, producing colliding or suffixed work emails (sarah.lee@ and sarah.lee2@).
Why it happens: name based email patterns guarantee collisions at any real company.
What it forces: proof that email is not a person identifier, and a uniqueness test on the person key.

### Data quality problems

**P08. Department name drift.** "Retail Ops", "Retail Operations", and "retail ops" all appear.
What it forces: a standardization mapping table, with a test that fails loudly when a new unmapped value shows up.

**P09. Inconsistent formats in matching fields.** Phone numbers with and without dashes and country codes, emails with mixed casing.
What it forces: standardization in staging before any matching runs, since dirty match keys produce silent failures.

### Reconciliation problems

**P10. The no show.** One candidate has a hired status and an accepted offer but never appears in PeopleCore.
Why it happens: people accept offers and never start, and someone forgets to update the recruiting system.
What it forces: a reconciliation check between the two systems, and a rule for which system wins. Here, the HRIS is the system of record for employment.

## 5. Business questions

The models exist to answer these questions. Working backward from questions is the design principle: if a model does not help answer one of them, it does not need to exist.

### Headcount

- How many people work at Northline today, overall and by department?
- How has headcount changed month over month?
- What is the split between full time, part time, and contract?

One definition to document and test: who counts in headcount. This project counts an employment record as active on a given day if the hire date is on or before that day and the termination date is either blank or later. The termination date itself is the first day not counted.

### Turnover and hiring

- How many people are hired and how many leave, by month and by department?
- Which departments lose people fastest?
- How does seasonal hiring show up across the year?

### Rehires

- How many current employees are rehires?
- Neither source system can answer this alone, because neither knows that two employment records belong to the same person. Only the person record built by this pipeline can answer it.

### Recruiting to employment

- What share of accepted offers convert into actual employment? This is the check that catches the no show (P10).
- Employees hired before 2022 have no recruiting record at all, so a missing candidate record is not evidence of a problem.

The dashboard covers headcount, hiring and turnover, and a third page explaining the data quality work.

## 6. Decisions log

A running record of design decisions made during the build, so a future reader can see not just what was decided but why.

| Date | Decision | Reasoning |
|---|---|---|
| 2026-07 | Distortions live in the generators, not the ground truth | Ground truth describes reality; each generator describes one system's flawed view of it. Keeps the answer key clean and puts each distortion next to the system that causes it. |
| 2026-07 | One planted problem per special person | If a match fails, there is exactly one possible explanation. Two problems on one person makes test results ambiguous. |
| 2026-07 | Simulation clock frozen at a fixed date | Using the real date would change tenure and termination outcomes every run, breaking reproducibility in a way the random seed cannot prevent. |
| 2026-07 | Trimmed planted problems from 13 to 10 | Depth over breadth. A smaller set that can be explained confidently is worth more than full coverage. Cut the three least visible problems. |
| 2026-07 | Rehires get a fresh suffixed work email, never their old address back | If a rehire's two records shared a work email, that field alone would link them and quietly remove the P04 challenge. |
| 2026-07 | Destructive distortions never touch special people; recoverable ones can | Blanking a field destroys a planted matching signal permanently. Formatting mess is fine on anyone, because cleaning undoes it. |
| 2026-07 | ATS only noise candidates are generated locally, not in ground truth | Ground truth is the answer key for identity resolution, so it only tracks people with a cross system identity question. Rejected candidates exist in one system and match nothing. |
| 2026-07 | Ground truth horizon extended to end of 2027; generators render "as of" a date | The company's full story is pre written and frozen. Each daily run exports only events that have happened by the run date, so real time passing reveals scripted changes. |
| 2026-07 | Every random choice is seeded per record, not per run | Otherwise a record's department drift, formatting, and IDs would reshuffle between daily exports, creating fake churn. Real systems are messy, but consistently messy. |
| 2026-07 | Seasonal hiring cycles baked into all years of history | Frontline hires peak in October and November with contracts ending in January, creating a repeating headcount rhythm the dashboard can surface and explain. |
| 2026-07 | Broadcast window churn tuned so headcount plateaus rather than declines | Early tuning produced 108 terminations against 51 hires, a company in collapse. Balanced flows read as healthy turnover instead. |
| 2026-08 | Snapshot reset once after the time travel demo | The snapshot held manufactured future history from testing. Dropping it and taking a fresh first capture means the recorded history starts from real operation. |
| 2026-08 | Dashboard reads purpose built aggregate tables, never the daily headcount fact | The daily fact stores a headcount per day, so summing it across dates counts people once per day worked. Aggregates make that mistake impossible in the BI layer. |
| 2026-08 | Department stored in the facts rather than joined by key | Eight values with no volatility do not justify a join in the BI layer. dim_department still defines the attributes. |
| 2026-08 | GitHub Actions triggers the daily run, Prefect still orchestrates it | Managed execution would require moving credentials and the dbt profile into a third party runtime. A scheduled workflow gets unattended daily runs while keeping Prefect as the orchestrator and its run history intact. |
